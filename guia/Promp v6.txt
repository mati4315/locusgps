PROMPT MAESTRO — DESARROLLO DE LA APP ANDROID

Quiero desarrollar una aplicación Android de navegación GPS personal siguiendo estrictamente la arquitectura definida en el proyecto “Navegador GPS personal con ubicación en tiempo real”, versión v6 — MapLibre + MapTiler + OpenStreetMap + GraphHopper + Hostinger + MySQL + puntos personalizados.

La prioridad absoluta es:

1. Navegación GPS rápida y fiable.
2. Bajo consumo de batería, datos móviles y servidor.
3. Arquitectura sencilla y mantenible.
4. Privacidad del usuario.
5. No depender de servicios innecesarios.
6. La IA debe ser completamente opcional y nunca puede ser necesaria para que funcione la navegación.

La aplicación debe sentirse como un navegador GPS moderno, sencillo y práctico, pero debe estar optimizada para ser utilizada por una sola persona con un único dispositivo Android.

---

1. CONCEPTO GENERAL

La aplicación será principalmente un navegador GPS personal.

El teléfono Android debe realizar localmente todo lo que pueda:

- obtener GPS;
- mostrar la posición;
- mostrar el mapa;
- seguir la ruta;
- calcular el progreso;
- detectar si el usuario se ha salido de la ruta;
- solicitar recálculo cuando sea necesario;
- mostrar puntos personalizados;
- detectar proximidad a cámaras/puntos de alerta;
- reproducir instrucciones de voz;
- mantener una caché local.

El servidor Hostinger debe actuar como una capa ligera de coordinación:

ANDROID
GPS
MAPA
NAVEGACIÓN
CACHÉ
ALERTAS
VOZ
        │
        │ HTTPS
        ▼
HOSTINGER
Node.js + Express
        │
        ├── MySQL
        ├── Routing Provider
        ├── Places / Geocoding Provider
        └── IA opcional

No convertir el servidor en un sistema que procese continuamente el GPS.

5. CÁLCULO DE RUTA

El routing debe estar abstraído mediante un proveedor.

La aplicación no debe quedar acoplada directamente a un único proveedor.

En la V1, el proveedor concreto de routing será GraphHopper, pero siempre detrás de una abstracción interna.

En el backend utilizar una interfaz conceptual:

calculateRoute(origin, destination, mode)

Para la V1 el proveedor seleccionado es:

- GraphHopper.

IMPORTANTE:
El backend debe mantener una abstracción `routingProvider`, de modo que GraphHopper pueda sustituirse en el futuro por OSRM, Valhalla u otro proveedor compatible sin modificar la aplicación Android.

No utilizar directamente desde Android la API de GraphHopper ni acoplar la app a su formato interno.

La Android app solamente debe conocer el formato de ruta que devuelve nuestra API.

Ejemplo:

Android
   ↓
POST /api/routes
   ↓
Hostinger
   ↓
routingProvider
   ↓
Ruta
   ↓
Android

22. PRIVACIDAD

La ubicación es un dato sensible.

Regla:

No enviar GPS continuamente al servidor.

Si el servidor necesita conocer la última ubicación por alguna función concreta, enviar solamente lo necesario y con una frecuencia baja.

La navegación normal debe funcionar sin enviar constantemente la posición.

No enviar la ubicación a la IA.

No enviar el historial GPS a servicios externos.

No guardar historial de trayectos salvo que posteriormente se implemente explícitamente esa función.

25. MAPA, MAPTILER Y OPENSTREETMAP

La V1 utilizará esta combinación:

- MapLibre Native Android = motor de visualización del mapa;
- MapTiler = proveedor de tiles;
- OpenStreetMap (OSM) = fuente de datos cartográficos.

Diferenciar claramente:

MapLibre = renderizado y gestión del mapa en Android
MapTiler = servicio que proporciona los tiles utilizados por MapLibre
OSM = datos cartográficos de referencia
GraphHopper = cálculo de rutas
Places/Geocoding = búsqueda y geocodificación

La aplicación NO debe descargar ni almacenar el mapa completo en MySQL.

No utilizar los servidores públicos de tiles de OpenStreetMap como backend ilimitado de producción.

Mantener el proveedor de tiles desacoplado de la lógica de navegación. La configuración de MapTiler debe estar centralizada para poder sustituir el proveedor de tiles en el futuro sin rehacer la arquitectura.

Respetar siempre:

- atribución de OSM y del proveedor correspondiente;
- políticas de uso;
- límites de solicitudes;
- condiciones de MapTiler;
- condiciones de GraphHopper;
- condiciones de cualquier otro proveedor utilizado.

No asumir que ningún servicio público o gratuito es ilimitado.

30. MANEJO DE ERRORES

La aplicación debe asumir que:

- no hay internet;
- el servidor no responde;
- el proveedor de routing falla;
- el proveedor de búsqueda falla;
- MySQL no está disponible;
- el GPS pierde precisión.

Nunca bloquear toda la aplicación por un fallo de un servicio secundario.

Ejemplo:

Routing falla
→ mostrar error
→ conservar navegación anterior si es posible

Puntos fallan
→ continuar navegación
→ utilizar caché disponible

IA falla
→ navegación y búsqueda normal siguen funcionando
